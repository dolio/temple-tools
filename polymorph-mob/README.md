# Polymorph Mob

## Info

This tool allows conversion and analysis of ToEE MOB files. These are used for
specifying the various objects that actually occur in maps, with each MOB
being an individual object. MOBs are able to specify every property of an
object, but they can also refer to a prototype, so that only differences from
that prototype need to be specified.

MOB files are a binary format, able to be dumped and loaded directly to
memory. This means they essentially require a tool to work with them. That
could be a dedicated ToEE module editing tool, and that is probably a good
idea when actually building a module. But for taking an existing MOB and
fixing some of its properties, I desired something that could just convert
between the binary format and a textual format, which is what this implements.

`polymorph-mob` has several modes.

### mob-to-json

This mode turns a binary MOB file into a JSON (like) file. It might not be
completely compliant JSON. For instance, some numbers are displayed in
hexadecimal, because I think that is more digestible for those fields.

The only required argument is the `.mob` file. An option allows specifying the
output file. If the latter is not specified, then the output file will just be
generated by appending `.json` to the original file name.

### analyze-mob

This mode reads in a binary MOB file and does a few checks. If errors are
encountered, then some information will be displayed about what happened
(unless suppressed). There are also options for looking for information in the
file, like a prototype id, which could be useful when searching for files
(since the file names are undescriptive GUIDs).

### mob-to-mob

This is mostly a diagnostic mode. It reads in a binary file and writes out a
binary file of the same object. Then the two can be compared or the result can
be substituted into the game to make sure it works.

Generally the output will _not_ be the same as the input. The MOB file format
just seems to be a memory dump of the in-game object. Since these are C
structures, they sometimes contain padding which will be filled with
uninitialized garbage, and that garbage ends up in the file. There is also
information like pointers or indices into transient tables that are just
directly dumped out, even though they are meaningless upon reloading.

Portions like this that have been identified have just been removed from the
structures, and instead `polymorph-mob` will write 0 for them instead of
random garbage.

### json-to-mob

This goes the opposite direction of the first mode. Given an appropriate JSON
file, this produces a binary file.

Many of the structures in the file are represented as JSON objects. Although
`mob-to-json` produces these in a fixed order, the order does not matter in
this mode, so you are free to rearrange things if desired. The parser should
also be relatively flexible with regard to the exact layout.

Like `mob-to-mob`, the result may not be identical to the original MOB file,
because garbage values will be replaced with zeroes.

### mdy-to-mobs

This handles a dynamic mob file from a saved game, usually `mobile.mdy`. This
is just a sequence of mobs packed into a single file.

The command takes an input file and an output directory, and creates
individual `.mob` files in the directory corresponding to the embedded
objects.


### md-to-json

This handles a mob diff file from a saved game, usuall `mobile.md`. This file
stores additional differences relative to the objects' .mob files.

The `.md` file does not contain enough information to be decoded stand-alone,
so a directory with `.mob` files for all the objects mentioned in the `.md`
file _must_ be provided.

By default, it is assumed that the same directory as the `.md` file contains
all the `.mob` files, but this unlikely assumption can be overridden with
`--map-dir` (named because the location of these `.mob` files are the
directories aggregating map assets). They are usually stored under the
`modules` directory of the ToEE install, possibly in a `.dat` file.

The output will be several `.json` files in the specified output directory.
These will be named by the UUID of the objects they modify, but will contain
only the differences from the original file.

### player-to-json

This handles created character files, either `.ToEEPC` or `.ToEEIMan`. These
contain mob data for the character with some extra player character
information. The full set of information is output to the JSON file.

## Conditions

Conditions are stored in MOB files according to their ELF hash, which is a
32-bit number. By default, `polymorph-mob` will just display the number when
converting to JSON, although you are free to write a string in the condition
arrays, and it will understand what to do with them.

If the `data/condition-names` file is installed to an appropriate location,
then the names in it will be hashed and used to decode numbers in MOB files
back into names, for better readability. You can add _any_ names to the file,
and they will be used for decoding, regardless of whether the conditions
actually exist in the game. The format of the file is just names separated by
linebreaks, and no trimming is performed at all (so be careful of
leading/trailing spaces).

The correct place to put the file is

    $XDG_DATA_HOME/polymorph-mob/condition-names

on Windows, this is under the `C:\Users\<user>\AppData\Local\` directory.
Elsewhere this is under `~/.local/share/` by default.

## Building

This program is written in Haskell. To build it, you must obtain a Haskell
installation. Visit

    https://www.haskell.org/

to learn how to get set up. GHC 9.10 was used to develop this, and the
specified dependencies are likely to require something approximately that new.

The project is set up to build with `cabal`, and once you have a Haskell
setup, should be able to be installed with

    cabal install polymorph-mob
